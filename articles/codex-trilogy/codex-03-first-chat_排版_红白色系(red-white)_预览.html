01

步骤 01 · 预计 2 分钟

完成第一次对话

启动 Codex，并确认模型能够正常回复


打开一个新终端，输入：

   bash

codex

第一次启动会进入 TUI 交互界面。直接发一句最简单的测试：

   text

你好，用一句话介绍你自己，并告诉我你是什么模型

如果几秒后收到流畅的回复——恭喜，端点、key、模型三样全通，你已经正式上车。正常情况你会看到类似这样的回答：

   text

我是 Codex，一个基于 gpt-5.6-sol 的 AI 编程助手，可以帮你读写代码、

调试问题、解释技术概念。

这一句测试同时验证了四件事：ziikoo 端点可达、token key 有效、gpt-5.6-sol 模型名正确、Responses 协议工作正常。任何一个环节错了，这里都会立刻报错，所以它是最好的验收动作。

02

步骤 02 · 预计 3 分钟

在项目中执行／init

让 Codex 读取项目并生成 AGENTS.md


对话通了，马上做一件有仪式感的事——让 Codex 接管一个项目的上下文。

随便建一个练习文件夹（以后换成你的真实项目也一样）：

   bash

mkdir codex-demo

   bash

cd codex-demo

   bash

codex

进入 TUI 后，输入斜杠命令：

   text

/init

执行成功，你会看到它生成了项目说明文件：

   text

✓ Created AGENTS.md

完成标志

✓ 项目根目录已经生成 AGENTS.md。

AGENTS.md 是 Codex 理解项目的“地图”：项目结构、技术栈、构建命令、代码规范，都写在里面。以后每次在这个目录启动 Codex，它都会先读这份文件，回答和改动都会贴着你的项目实际走。

空目录下它生成的内容很简略，这很正常。真正的威力在你把它放进一个真实项目的那天：代码库越大，/init 省掉的解释成本越多。

交付一个真实任务

在同一个会话里，给它一个带点工程量的小任务，感受一下 GPT-5.6 Sol 的 coding 能力：

   text

在当前目录写一个 Python 的快速排序实现，带类型标注和 doctest，然后运行测试确认通过

看着它自己写文件、跑测试、修问题——这一整套闭环，就是你这三篇教程换来的东西。

04

步骤 04 · 预计 1 分钟

遇到问题再排查

主流程失败时按症状快速定位配置问题


报错 / 大概率原因
怎么修
401 Unauthorized｜token key 错了或已失效
回 ziikoo 控制台重新创建 key，在 CC Switch 里更新并重新启用
404 Not Found｜Base URL 不对
检查必须是 https://api.ziikoo.com.cn/v1，带 /v1、末尾无斜杠
模型不存在 / model not found｜模型名打错
一个字一个字核对：gpt-5.6-sol
一直转圈 / 超时｜网络层问题
关掉终端里的代理环境变量再试；国内直连 ziikoo 端点不需要挂代理
配置不生效｜改完没重新启用
回 CC Switch 确认 ziikoo 是「启用」状态，再重启 codex

90% 的问题都出在前三行。修完重新执行 codex，再发一次测试句。
