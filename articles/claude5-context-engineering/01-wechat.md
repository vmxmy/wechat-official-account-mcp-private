# Claude 砍掉 80% 系统提示词之后：上下文工程的新规则

你打开 `CLAUDE.md`，又加了三条规矩：

「不要写注释」「必须写注释」「按文档写注释。」

同一条对话里，系统提示、Skill、用户需求互相打架。模型不是笨，是被你绑住了。

Anthropic Claude Code 团队的 Thariq 最近写了一篇很长的复盘：在 **Claude Opus 5 / Claude Fable 5** 这代模型上，他们把 Claude Code 系统提示词砍掉了 **超过 80%**，编码评测几乎没有掉分。

结论很刺耳，也很实用：

> **以前靠规则拴住模型；现在要学会松绑，把判断权还回去。**

下面按原文把「旧神话 → 新规则」拆开，并落成你今晚就能改的清单。

---

## 一、30 秒说清发生了什么

你发给 Claude 的那句 prompt，只是上下文的一小块。

真正撑起一整次会话的，还有：

- **System Prompt**（产品级行为）
- **Skills**（按需加载的能力说明）
- **CLAUDE.md**（仓库约定与坑）
- **Memory / Artifacts / 引用文件**

Anthropic 把这套组装工作叫 **Context Engineering（上下文工程）**。

它和单次 prompt 最大的不同：  
**上下文会被反复复用，不能写得太具体。**  
你必须在「足够通用」和「足够有用」之间找平衡——而模型能力一变，平衡点就得跟着变。

他们在内部 transcript 里看到的典型事故不是模型不懂，而是：

同一请求里同时出现「按情况补文档」和「绝对不要加注释」。  
Claude 往往仍能猜对用户意图，但得先在冲突指令里多绕一圈。

旧模型时代，这些硬约束是为了避免删文件、乱写注释之类的最坏情况。  
新模型判断力上来之后，**很多护栏可以删，让模型读周围代码自己做决定。**

## 二、六个「以前 vs 现在」

这是全文最值得截图的部分。

| 以前（已成神话） | 现在（Claude 5 代） |
|---|---|
| 给 Claude 立规矩 | 让 Claude 用判断力 |
| 堆使用示例 | 把工具接口设计好 |
| 所有信息一股脑塞前面 | 渐进披露，用到再加载 |
| 同一条指令重复写 | 工具描述写清就够 |
| 记忆写进 CLAUDE.md | 自动记忆 |
| 简单 Markdown 规格书 | 更丰富的引用（代码、HTML、评分标准） |

### 1）规矩 → 判断

旧系统提示里有过这种强度：

> 默认不写注释；不要写多段 docstring；不要主动写规划/分析文档……

在一部分任务上这是对的；在另一部分任务上，这是在帮倒忙——复杂模块、团队文档习惯、用户明确要求，都会撞车。

新写法更像：

> **写得像周围的代码：注释密度、命名、习惯都对齐。**

一句话，把「禁止清单」换成「跟现场」。

### 2）示例 → 接口设计

以前教模型用工具，第一定律是：**多给 examples。**

现在他们发现：示例会把探索空间焊死在示例路径上。

更有效的做法是：想清楚工具参数本身有多「会说话」。

比如 Todo 工具：

- `status` 只允许 `pending / in_progress / completed`
- 并约定 **同时只有一项 in_progress**

不用长篇示例，模型也能读懂该怎么用。

**少讲故事，多把枚举、约束、接口语义设计对。**

### 3）全塞前面 → 渐进披露

早期 Claude Code 系统提示里塞满了 code review、验证流程——不是每次都用到，但一旦用到就很关键。

现在他们更相信 **progressive disclosure**：

- 验证、评审拆成独立 Skill，需要时再调用
- 部分工具 **deferred loading**：先搜到定义（如 ToolSearch），再用，避免常驻吃上下文

对应到你自己的仓库：

别把 `CLAUDE.md` / `SKILL.md` 做成「宇宙百科全书」。  
做成 **一棵会按需打开的文件树**。

### 4）重复叮嘱 → 工具描述写清楚

老模型有时对上下文末尾更敏感，于是系统提示里重复提工具，工具 description 里再写一遍。

新模型上，重复可以砍掉：  
**怎么用工具，写进工具描述；系统提示别再当小抄本。**

### 5）CLAUDE.md 当记忆本 → Auto-memory

以前鼓励用 `#` 热键往 CLAUDE.md 记东西。  
现在 Claude 会自动保存对你、对当前工作有用的记忆。

CLAUDE.md 该回到本职：**仓库地图 + 本地坑**，不是日记本。

### 6）简单规格 → 丰富引用

Plan 模式曾经重度依赖 Markdown 计划文件。  
现在模型能啃更复杂的引用：

- Artifacts 生成的 **HTML**
- **测试套件** 当规格
- 另一仓库里要移植的 **真实函数**
- **Rubrics（评分标准）**：用来启动 verifier agent，对齐「什么叫好的 API 设计」这类品味问题

一句话：  
**能给代码就别只给形容词。**

## 三、落到你仓库：四层上下文怎么写

### System Prompt

产品级身份与任务边界。

- 用 Claude Code：你基本 **不用改**
- 自建 agent harness：这里值得花最多时间

### CLAUDE.md

保持轻：

- 几句话说明 **这个仓库是干什么的**
- 大部分 token 留给 **仓库特有坑**（例如：类型只能写在某个 monofile，别处禁止）
- **别写「打开文件就能看懂」的废话**

细节用渐进披露：验证流程很长？做成 verification skill，再在 CLAUDE.md 里点一下引用。

### Skills

把 Skill 想成 **轻量导航**，不是厚说明书。

- 非关键路径：少硬约束
- 关键路径：可以严一点
- 长 Skill：**拆文件**，用到再加载
- 最有价值的内容：你们团队 / 产品 **特有** 的意见、知识和最佳实践

别人写得出的通用教程，不配占你的 context。

### References

用 `@` 把规格、 mockup、整段代码库挂进来。

优先顺序建议：

1. **代码本身**（高保真）
2. **HTML mockup**
3. 纯文字描述 / 截图

「做成什么样」用界面和代码说，比形容词准一个量级。

## 四、今晚可执行的精简清单

对照 Thariq 的建议，按顺序做：

1. **跑一遍** Claude Code 里的 `/doctor`（文中也写作 `claude doctor`），给 Skills 与 CLAUDE.md 做 rightsize  
2. **搜冲突**：同一仓库里是否同时存在「必须注释 / 禁止注释」这类对冲句  
3. **砍通用常识**：能从目录结构和代码读出来的，删  
4. **把流程迁出 CLAUDE.md**：评审、验证、发布 → Skill 或 deferred 工具  
5. **示例改接口**：工具 description 里用枚举和约束，而不是长 example 堆  
6. **记忆搬家**：别再把个人偏好往 CLAUDE.md 塞；交给 auto-memory  
7. **规格升级**：重要任务给测试、参考实现或 rubric，而不是再写一篇「请务必优雅」

如果只记一句：

> **上下文工程的新默认值，是减法，不是加法。**

## 五、和前一代习惯怎么兼容

旧习惯不是「错」，是 **为弱判断力模型买的保险**。

模型强了之后，保险本身会变成摩擦：

- 约束越多，冲突越多  
- 冲突越多，模型越要在指令丛林里做二次推理  
- 你以为在「更安全」，其实在「更慢、更拧」

所以这次 Anthropic 内部能砍 80% 系统提示还不掉分，不是魔法，是：

**模型已经会看现场；你还在念 combative 版员工手册。**

当然——删除不等于放飞：  
删的是过时硬规矩；保留的是产品边界、安全红线、以及**只有你知道的仓库坑**。

## 结尾站队

如果你还在给每个模型堆 200 行「永远 / 绝不 / 必须」：

先别急着再装 Skill。  
先删掉互相打架的那几段。

**强模型时代，最好的上下文工程，往往是：少写一点，写对一点，写到用到再展开。**

你准备先砍哪一类？

- A：互相矛盾的注释/文档规矩  
- B：塞满「常识」的 CLAUDE.md  
- C：一打开就吃上下文的巨型 Skill  

评论区回一个字母就行。
