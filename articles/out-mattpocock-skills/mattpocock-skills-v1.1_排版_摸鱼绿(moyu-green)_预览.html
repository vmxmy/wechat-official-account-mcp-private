Superpowers 给 Agent 超能力；我的 skills 给你超能力。

如果你还在用一句话甩需求 → 等代码 → 再骂它不懂，那你和半年前的 vibe coding 没有本质区别。

Total TypeScript / AI Hero 作者Matt Pocock把自己日常.claude目录里的实战 skill 开源了：mattpocock/skills。截至 2026 年 7 月，仓库约17.5 万 Star；最新正式版v1.1.0（2026-07-08）把主流程从「会问会写」推到「能跨会话规划、能验收、能评审、能并行拆票」。

Twitter/X 上不止是屠榜情绪：有榜单显示单日星标仍在 +1.9k 量级；Matt 本人也提过仓库一度16 万 Star + 750 万次下载却几乎没有教程，于是补了端到端 walkthrough。更有价值的是作者与用户晒出的可抄实操——本文后半段单独成章。

我们只拆v1.1 真正补上的闭环，并把推特上已经验证过的做法写进正文。

为什么这篇值得读

WHY IT MATTERS

社区热度只是引子。真正值得读的，是它正面回应了四个Agent 常见翻车——而不是再发明一套接管你流程的大框架。

Matt 反复强调：这些 skill小、可改、可组合，基于几十年工程经验，而不是用 GSD / BMAD / Spec-Kit 那种「接管过程」的方式剥夺你的控制权。

04

PART

v1.1 主轴：从「会问」到跨会话交付

THE MAIN SPINE

v1.0 已经把User-invoked / Model-invoked分清：你手动触发的负责编排，模型可自触发的负责纪律。v1.1 的增量，集中在把「想法 → 可交付」做成可导航的地图，而不是一场超长对话。

日常默认门（主流程）

. . . text

idea

→ /grill-me 或 /grill-with-docs

→ /to-spec

→ /to-tickets

→ /implement（内驱 /tdd）

→ /code-review

迷路时先/ask-matt：v1.1 补全了 tdd、diagnosing-bugs、domain-modeling、codebase-design、grilling 等路由，并新增Something's broken入口——以前坏了不知道从哪条 skill 进。

超大任务旁路：/wayfinder

不是新的默认脊柱（Matt 明确说：把 wayfinder 捧成默认主链是v2 级改动），而是情境入口：绿地上项目 / 巨型功能，一会话装不下；从 grill 发现「雾太大」，需要先画地图。

1

目的地优先：地图有 Destination，一切票围绕它

2

计划，不交付：产出决策，不是代码；雾散了再进实现链

3

地图是索引：决策只活在 ticket 里，地图只摘要 + 链接，防双写

4

HITL vs AFK：该人类拍板的票绝不能让 Agent 自问自答；研究类可 AFK

5

无雾早退：开场 grill 若无雾，直接进常规单会话流程，不硬造地图

！踩坑提示 🕳

社区吐槽 Agent 用 grill「自己问自己」。v1.1 在 wayfinder 与 grilling 两侧一起堵。

作者本人最近在用的升级路径

Matt 在 2026-07-17 公开的新习惯流非常短，却极有用：

. . . text

1. /grill-with-docs

2. 「我靠，这比我想的大多了」

3. /wayfinder 给这件事画地图

4. 继续干活

落地话术：先 grill 测体积；一发现雾太大，立刻 wayfinder，不要硬撑单会话。

他自己用 wayfinder 规划整门课程时写过：连续四天、接近100 次 grilling / prototyping / research 会话，全部回灌到一张会长大、也会缩小的中央地图——雾变清晰就毕业成决策，答案出现就从地图上消掉。这不是 demo 文案，是作者级真实工作负载。

05

PART

五个最值得抄的 v1.1 硬改动

FIVE HARD UPGRADES

SKILL 1

Grilling：确认闸门 + 事实/决策二分

这是 Twitter 上传播最广的修复。

确认闸门：在你明确确认「我们已经对齐」之前，Agent不得开始执行计划。旧版把「共享理解」当完成条件，模型容易自行宣布「对齐了」。

事实 vs 决策：事实 → 去代码库/文档里查；决策 → 必须问人，并等待回答。旧规则「能靠探索代码库回答的就去探索」在「解 ticket」场景被滥用成「决策也自己拍」。二分之后，grilling 才是真 HITL，而不是表演式问答。

自测句：你用/grill-me时，Agent 是在等你确认，还是先猜答案再假装提问？

SKILL 2

规划统一：to-spec + to-tickets

to-prd →/to-spec（规格一词贯穿全链路）；to-plan + to-issues →/to-tickets。

每张 ticket 是tracer-bullet 垂直切片，并声明 blocking edges：本地 tickets.md 边写成文字；真 tracker 边写成原生阻塞关系，无阻塞票可并行多 Agent。另：教 wide refactor（列改名等爆炸半径铺满全库的机械改动）走 expand–contract，避免一刀切永远绿不了。

SKILL 3

code-review 毕业 + Fowler 坏味道基线

review 从 in-progress 毕业为/code-review，并挂进 /implement 收尾。双轴并行（子 Agent 互不污染）：

1

Standards——仓库规范 + 内置约 12 条 Fowler Bad Smells（神秘命名、重复代码、特性依恋、数据泥团、散弹式修改……）

2

Spec——是否忠实实现 originating issue / 规格

✦ 两条硬约束

仓库文档标准优先于基线；味道是判断建议，不是硬违规。

SKILL 4

新增 research：背景 Agent 读一手源

Model-invoked：对官方文档、源码、规格、一手 API做调查，落一份带引用的 Markdown。你继续干主线，它帮你做「可烧烤的阅读底稿」。

SKILL 5

writing-great-skills：否定与负空间

写 skill 的人必读。两个新失效模式：

模式问题疗法
Negation（大象）「不要做 X」反而把 X 拉进上下文写正向要做什么
Negative Space（虚空）省略的决策被模型先验填满刻意审沉默：补全或标成 branch

你以为关掉的开关，其实还在导流。

06

PART

TDD 与 prototype：信模型，也防假绿

TDD & PROTOTYPE

TDD 变 reference-only：红→绿由模型已内化的 leading word 驱动，删掉重复 Workflow；重构归 review 阶段。引入seam——只在与用户预先约定的缝上写测。新增同义反复测试反模式：断言用和实现同一套算法重算，测了等于没测。

prototype 改为 model-invoked：Agent 可在「状态/逻辑摸底」或「UI 多方案探索」时自己伸手，产物是可扔的回答设计问题的代码，不是半永久功能分支。

PART

推特上的可抄干货

FROM X · ACTIONABLE

下面几条不是情绪热评，是可以直接搬进你工作流的可验证做法。

CASE 01

Wayfinder 解决「grill 问到崩溃」

开发者 Nick 实测：一次51 问的 grill-me 中途 compact 后信心崩掉，改从 wayfinder 重开，结论是：

1

Wayfinder更会画边界；grill-me 在你不熟的领域容易越跑越偏

2

有的 ticket 像 grill（要人），有的纯 research（可 AFK，不挡你）

3

地图让你敢compact / 换新 Agent再续，上下文对新手线程仍然好用

✦ 对应产品逻辑

这和 v1.1 的 HITL / AFK 分类、确认闸门是同一条产品逻辑。

CASE 02

把自定义 skill 挂进 Wayfinder 当编排器

Will Ness（Matt 亲自转发并点赞）：基于 grilling + prototype 做了一套前端专用变体——

1

让 Claude 先做5 个差异极大的原型

2

做一个live picker现场切换

3

每轮选中意的分支 + 反馈，沿设计树缩小范围

4

写回 wayfinder：凡是新地图里出现 novel frontend 工作，自动生成 ticket，强制走这套 frontend grilling

Matt 点评：把/wayfinder 当自定义 skill 的编排器；多阶段原型是在上下文里一次只 zoom 一块 UI。

公司规范不要散落成口头习惯，写成 skill，再挂到 wayfinder 的 ticket 类型上。

CASE 03

批量烤问：13 问从 13 轮压到 3 轮

Matt 自己在推：/batch-grill-me 体感明显好于逐题/grill-me：

对比BeforeAfter
轮次13 问 = 13 轮13 问 = 3 轮
策略逐题串行只问 frontier
研究堵在对话里background agent

仍然只问frontier（不依赖其他未决决策的问题）；研究类任务丢给 background agent，不堵 grilling。若你也嫌 grill 太「一问一答 intermediate」，优先关注 batch / 多题并行形态（官方 skill 名以你安装版本为准）。

CASE 04

中文社区的二次工程化

有开发者开源了基于 grilling 的优化版：提高问题质量、降决策成本、反噪音与反过度设计；最大改动是优先用运行时request_user_input / AskUserQuestion真提问，而不是让模型在文本里假装等你。

✦ 方向正确

把 HITL 接到 harness 的真实交互原语上。

CASE 05

定位口令：给谁超能力？

Matt · 选型先问这一句

Superpowers gives the agent superpowers · My skills give you superpowers

选型时先问：你要的是Agent 更会自己干，还是你更会指挥 Agent？两套可以共存，别混成一团提示词。

社区在吵什么、你该警惕什么

CAVEATS

1

可复用 > 一次性聪明：技能要可检查、可版本化、可组合——不是聊天记录里的「那次挺灵」。

2

Harness 碎片化：这套为 Claude Code 的斜杠调用优化，在 Codex 等 harness 上体验可能不一致。落地时先确认你的 Agent 如何加载 Agent Skills 标准。

3

二次魔改正在发生：正确姿势是当基础协议，而不是当宗教。

4

星标 ≠ 你公司能用：真正 ROI 来自 setup 一次、统一术语、默认走 grill→spec→tickets，并在 code-review 用仓库标准覆盖 Fowler 基线。

给你的 7 天落地清单

7-DAY PLAYBOOK

STEP 01

Day 1 · 安装

装 skill + 跑 setup-matt-pocock-skills；选 tracker。

STEP 02

Day 2 · 强制 grill

挑一个真实小需求，强制 grill 到你口头确认对齐才允许写码。观察：它是否还在替你做产品决策。

STEP 03

Day 3 · 共享语言

给主项目建或补 CONTEXT.md（10～30 条领域词）。对比补前后的 token 与命名一致性。

STEP 04

Day 4 · 拆票

用 to-spec + to-tickets 拆一张中等功能；检查每张票是否有阻塞边，能否并行。

STEP 05

Day 5 · 实现

开 implement，约定 test seam；拒绝 tautological tests。

STEP 06

Day 6 · 评审

强制 code-review；把 1～2 条反复出现的 smell 写进仓库 coding standards。

STEP 07

Day 7 · 大雾 + 编排

跨周大项跑 wayfinder；若有团队规范，写成 skill 并挂到 wayfinder ticket 类型上。

EPILOGUE

Twitter 上那句patterns every senior dev uses unconsciously点破了价值：资深工程师的「多问一句、先对齐、再垂直切片、再评审」不是玄学；AI 时代的差异，是这些纪律能否可安装、可组合、可在 PR 里被检查。

mattpocock/skillsv1.1的意义，不是又堆了几个 slash command，而是：

1

用确认闸门 + 事实/决策二分堵住「Agent 自问自答」

2

用 to-spec / to-tickets / implement / code-review 收束交付链

3

用 wayfinder 诚实承认：有些工作一会话装不下，该先画雾中的地图

4

用 writing-great-skills 教你写下一层——你自己的团队 skill，并挂回编排器

npx skills@latest add mattpocock/skills
