# 17.5 万 Star 的 Skills 更新：真正缺的不是更强 Agent

> Agent 越强，越不能把事实、决策、规划、实现与审查全部塞进同一个黑盒。

一条版本发布帖，超过 3500 次点赞，约 24.6 万次浏览。

三天后，Matt 又专门发帖解释推荐工作流，依然获得超过 1400 次点赞。

问题来了：一个 Skill 仓库的 Minor Release，为什么会引起这么大反响？

因为 `mattpocock/skills v1.1.0` 没有继续讲“怎样让 Agent 做更多”，而是开始回答一个更棘手的问题：**项目变复杂以后，人和 Agent 到底应该怎样分工？**

答案不是再写一条万能 Prompt，而是把调研、决策、规划、实现和审查拆成一组可检查的中间状态。

这篇文章不逐条翻译 Release Notes。我们只讲三件对开发者真正有用的事：工作流变了什么、社区为什么关注，以及你明天可以怎样用。

> **怎么读这篇文章？** 每个 Skill 模块都写清了适用场景、职责边界和真实开发 Prompt。你不用背整套框架，找到与当前任务最接近的模块，把提示词里的业务背景、技术栈和限制条件换成自己的，照着写就够了。

## 3500 个赞背后：大家追的不是新 Skill

先看最直观的变化：原本分散的规划工具，被收进一条主流程。

```text
idea → to-spec → to-tickets → implement → code-review
```

如果面对的是一个大到单次 Agent 会话装不下的项目，则先进入：

```text
wayfinder → to-spec → to-tickets → implement → code-review
```

旧的 `to-prd` 被重命名为 `to-spec`，`to-plan` 与 `to-issues` 被合并进 `to-tickets`。这不只是命名调整，它在统一整个系统对“中间产物”的理解：先形成明确规格，再拆成有依赖关系的交付任务，最后进入实现和审查。

真正重要的变化是，Agent 不再被期待从一句模糊需求直接冲到代码，而是必须经过一组可检查的中间状态。

## Wayfinder 很火，但最容易被用错

`wayfinder` 是本次更新最火的能力，也是最容易被误解的能力。

它不是“更强的项目经理 Agent”，更不是所有项目的新默认入口。它只解决一类问题：绿地项目、大型功能，或者任何无法装进一个会话的工作。

它使用的隐喻不是“项目计划”，而是“战争迷雾”：你知道目的地，却不知道所有路径。Agent 的任务不是假装一开始就拥有完整答案，而是逐步暴露未知、建立任务之间的阻塞关系，并找出当前可以推进的 Frontier。

一张 Wayfinder 地图主要回答四个问题：

1. Destination：最终要到达哪里；
2. Not yet specified：范围内还有什么没有弄清楚；
3. Out of scope：哪些工作已经明确排除；
4. Frontier：哪些任务已经没有前置阻塞，可以立即推进。

地图本身不保存所有细节。每项研究、决策或原型都进入独立 Ticket，地图只保留摘要和链接。这使它更像共享索引，而不是又一份会迅速过期的大文档。

Matt 后续特别澄清：`wayfinder` 不是新的万能入口。地图稳定以后，编码工作仍然应该转入 `to-spec`、`to-tickets` 和 `implement`。它负责找路，不负责替整个团队走完全程。

### Prompt 示例：把订阅制 SaaS 改造成按量计费

```text
/wayfinder
我们要把现有单体 SaaS 从按席位订阅改为按 API 调用量计费。
系统使用 Stripe、PostgreSQL 和三个异步 Worker，已有约 2 万个付费租户。
目标是在不中断现有订阅的情况下，上线计量、账单预览、超额提醒与迁移方案。
请先建立 Destination、Not yet specified、Out of scope 和 Ticket 依赖图。
把事实调查交给 research，需要业务取舍的节点标为 HITL。
暂时不要修改代码；如果工作量能在一个会话内完成，请提前退出并说明原因。
```

## 真正的升级：把决策权还给人

Wayfinder 负责找路，但这还不是 v1.1.0 最重要的变化。

真正值得开发者关注的，是它开始明确规定：哪些事可以交给 Agent，哪些事必须停下来等人。

### MODULE 01｜Ask Matt：不知道从哪开始，就先问路由器

`ask-matt` 是用户主动调用的总入口。它不直接替你实现功能，而是根据当前处境，把任务引导到合适的 Skill 或工作流。

v1.1.0 补齐了它此前遗漏的多个路由，包括 `tdd`、`diagnosing-bugs`、`domain-modeling`、`codebase-design` 与 `grilling`；同时把 `prototype`、`research` 和 `wayfinder` 纳入更完整的入口说明。

这意味着开发者不必先记住整套 Skill 名称。遇到 Bug、架构语言混乱、需求不清或大型项目时，可以先调用 `ask-matt` 描述处境，再由它选择下一步。它更像一个工作流导航台，而不是另一个执行 Agent。

#### Prompt 示例：支付回调偶发重复订单

```text
/ask-matt
生产环境的支付 Webhook 偶发重复创建订单，每周约 3～5 次。
日志显示同一个 event_id 在 30 秒内到达两次，但数据库没有唯一约束。
我不确定应该先诊断、调研第三方重试规则，还是直接用 TDD 修复。
请检查当前仓库和已有 Issue，把这个问题路由到合适的 Skill 与流程。
先说明推荐路径和理由，不要直接修改生产代码。
```

### MODULE 02｜Research：事实交给 Agent 查

新的 `research` 会在后台代理中检索官方文档、源代码、技术规范和第一方 API，并把结果整理成带引用的 Markdown 文档。

它解决的是阅读型工作：主 Agent 可以继续处理当前任务，研究 Agent 在后台补齐事实证据。

#### Prompt 示例：验证 Cloudflare Workers 中的 Stripe 签名

```text
/research
调查在 Cloudflare Workers 中验证 Stripe Webhook 签名的正确实现。
只使用 Stripe 官方文档、Cloudflare 官方文档和相关 SDK 源码。
重点确认原始请求体读取、Web Crypto 支持、时间容差与重放攻击防护。
对比 stripe-node 与手写验签的运行时限制，并给出适用于当前仓库的建议。
把带引用的结论写入 docs/research/stripe-workers-webhook.md。
不要修改业务代码，也不要引用二手博客作为事实来源。
```

### MODULE 03｜Prototype：用一次性代码回答设计问题

`prototype` 适合在正式实现前验证状态逻辑或 UI 方向。它的产物用于回答问题，而不是直接进入生产环境。

#### Prompt 示例：验证企业权限编辑器的交互

```text
/prototype
为企业管理员做一个角色权限编辑器原型。
真实场景包含 500 个权限点、20 个内置角色、搜索、批量选择和继承关系。
请制作两个可点击方案：按资源分组的矩阵视图，以及搜索优先的命令面板视图。
使用模拟数据，验证管理员能否在 2 分钟内找出并撤销高风险权限。
记录两种方案的状态复杂度和可访问性风险。
这是一次性原型，不接生产 API，不迁移现有组件，不把原型代码当最终实现。
```

### MODULE 04｜Grilling：决策必须交还给人

`grilling` 现在明确区分事实和决策。事实可以通过代码库和资料查证；产品取舍、范围边界与风险偏好则必须询问用户。

新版还增加了确认门：在人类确认双方已经达成共同理解之前，Agent 不得直接执行方案。

这是一个看似保守、实际非常关键的设计。很多 AI 编程失败并不是模型不会写代码，而是它悄悄替用户完成了本应由用户作出的决定。

#### Prompt 示例：澄清企业 SSO 的产品决策

```text
/grill-with-docs docs/sso-requirements.md
我们准备为企业版增加 SAML SSO，但文档没有明确多 IdP、域名认领和即时停用策略。
请先从代码库确认现有租户、成员和会话模型，这些属于事实。
涉及登录回退、强制 SSO、生效范围和迁移窗口的内容属于产品决策，请逐项问我。
每次只推进一个关键决策，并记录已确认结论与未决问题。
在我明确确认共同理解之前，不要生成实施计划，也不要修改代码。
```

### MODULE 05｜To-spec 与 To-tickets：把理解变成可交付结构

`to-spec` 负责形成清晰规格，`to-tickets` 则将规格拆成纵向切片，并显式记录阻塞关系。

对于跨越整个代码库的机械式重构，新版引入 Expand–Contract 思路：先让新旧形式并存，再分批迁移调用方，最后删除旧形式。目标是让 CI 在每个批次后尽量保持可用，而不是制造一个长期无法合并的巨型分支。

#### Prompt 示例：无停机迁移租户主键

```text
/to-spec
把 PostgreSQL 中 tenants.id 从自增 INT 迁移为 UUID。
该字段被 38 张表、Kafka 事件和公开 REST API 引用，迁移期间不能停机。
规格必须覆盖双写、回填、读路径切换、外部 API 兼容、回滚条件和可观测性。
不要假设可以一次性修改全部调用方。

/to-tickets
把确认后的规格拆成 Expand–Contract 任务。
每个 Ticket 都要给出验收条件、阻塞关系、可独立验证方式和回滚边界。
优先让每批迁移后的主分支保持绿色；无法独立绿色的步骤集中到最终集成 Ticket。
```

### MODULE 06｜TDD：只负责 Red → Green

TDD 被收敛为 Red → Green。重构阶段被移交给 `code-review`，测试只应该写在预先确认的系统接缝上。

同时，新版增加了“同义反复式测试”反模式：如果测试用与实现相同的方式重新计算期望值，它即使通过，也不能提供真实信心。

#### Prompt 示例：用 TDD 修复 Webhook 幂等性

```text
/tdd
修复同一个 payment event_id 被重复处理时创建两笔订单的问题。
建议测试接缝为 handlePaymentWebhook(event, orderStore)，但写测试前请先与我确认。
先写一个能稳定复现重复投递的失败测试，期望值来自唯一 event_id 业务规则。
再实现最小改动让测试变绿，并覆盖并发到达场景。
不要在本阶段重构周边模块；不要用实现内部的去重算法重新计算期望值。
```

### MODULE 07｜Code Review：重构与质量审查在这里发生

正式发布的 `code-review` 加入一组 Fowler 代码坏味道作为持续生效的参考基线，包括重复代码、特性依恋、数据泥团、霰弹式修改和过度设计等。但项目自身规范拥有更高优先级，坏味道只能作为专业判断，不能被当成机械违规。

#### Prompt 示例：审查幂等性修复分支

```text
/code-review
审查 feat/webhook-idempotency 相对 main 的改动。
先读取仓库 AGENTS.md、数据库约束规范和错误处理约定，它们优先于通用规则。
重点检查并发安全、事务边界、唯一索引迁移、重试行为和测试是否真正独立。
使用 Fowler 坏味道作为参考，但每项都标明这是判断而不是硬性违规。
按阻塞、重要、建议三级输出，并为每项提供文件位置和证据。
只做审查报告，不要直接重写代码。
```

## 社区开始分化：有人编排，也有人质疑

从 Grok 对 X 的搜索结果看，热度几乎都集中在 `wayfinder` 和完整工程链路上。这说明大家关注的已经不是单个 Skill，而是怎样把多个 Agent 能力组织起来。

官方发布帖获得超过 3500 次点赞，Matt 随后发布的工作流澄清也获得超过 1400 次点赞。Will Ness 分享的实践，则把传统的 Research → Plan → Implement 概括为更动态的 Goal → Task → Adjust 循环。

更有意思的是，社区开始把 `wayfinder` 当成自定义 Skill 的轻量编排器：把前端访谈、研究、原型验证等能力挂到地图节点上，每次只加载当前任务需要的上下文。

但社区也并非只有赞美。

少量反馈提到 `to-tickets` 仍可能出现术语漂移和输出一致性问题。这提醒我们：Skill 提供的是结构和约束，不是确定性编译器。

**越依赖 Agent 自动生成中间产物，越要保留人工检查点。**

## 别全套照搬：按项目大小选入口

看到这里，最容易犯的错误是：把整条流程复制到每一个任务里。

没有必要。更合理的方式，是根据不确定性和工作规模选择入口。

如果连任务属于哪一种都不确定，就先从 `ask-matt` 开始，让它把问题路由到调试、访谈、建模、原型或完整交付链路。

### 小型、边界清楚的修改

```text
implement → code-review
```

例如修复一个定位清楚的 Bug、增加一个小字段，或者完成一个已经写明验收条件的任务。此时不需要为简单工作制造地图和规格文档。

### 中型功能或存在需求分歧

```text
grill-with-docs → to-spec → to-tickets → implement → code-review
```

先从现有 Issue、设计文档与代码库中建立共同理解，再形成规格和交付切片。

### 大型项目或跨多个会话

```text
wayfinder → to-spec → to-tickets → implement → code-review
```

先明确 Destination 和未知区域，再将研究、人工决策、原型与任务挂到共享地图中。地图足够清晰后，才进入常规交付链路。

## 升级前，先在仓库里搜一遍旧名字

虽然官方将 v1.1.0 标为 Minor Release，但旧提示词、脚本和项目文档可能受到以下变化影响：

| 旧名称 | 新名称 |
|---|---|
| `to-prd` | `to-spec` |
| `to-plan` | `to-tickets` |
| `to-issues` | `to-tickets` |
| `review` | `code-review` |
| `decision-mapping` | `wayfinder` |

升级后，应搜索仓库中的旧 Skill 名称，同步修改 `AGENTS.md`、`CLAUDE.md`、自动化脚本与团队文档。

## 结语：AI 编程下半场，拼的是边界

回头看，v1.1.0 最有价值的地方，不是新增了一个会画地图的 Agent。

它真正重新定义的，是“自动化应该停在哪里”。

事实可以交给 Agent 调研，代码可以交给 Agent 实现，依赖关系可以交给系统维护；但产品决策、目标边界和关键取舍，仍然需要人类确认。

AI 编程正在从“让模型写更多代码”，转向“让团队拥有更可靠的协作结构”。

当 Agent 越来越强，真正稀缺的就不再是执行能力，而是清晰的目标、可验证的中间产物，以及不被自动化越过的决策边界。
