01

TL;DR

太长不看

一句话：Emil Kowalski 的 skills 把「该不该动、怎么动」编码成 Agent 可执行规则，专治 AI 味界面。

装这个：

. . . bash

npx skills@latest add emilkowalski/skills

仓库： github.com/emilkowalski/skills （注意是 skills 复数，网上常写成单数 skill）。

六个 skill 怎么选：

场景 用哪个
日常写 UI / 动效 emil-design-eng
不知道该不该加动画 find-animation-opportunities
PR / 出活前审查 review-animations
整页动效太乱要治理 improve-animations
说不清「那种弹一下」 animation-vocabulary
要 sheet / 手势 / 流体感 apple-design

只记三条规则：

1

频率决定要不要动——快捷键、命令面板等超高频路径：不要动画

2

进场用ease-out，别用ease-in

3

不要scale(0)；popover 从 trigger 长出来（Modal 居中除外）

10 MIN

最小行动：对最近一页 Agent 生成的 UI 说——「什么该动、什么不该动？拒绝项必须写。最多 5 条建议。」


02

PAIN

你一定见过这种「能用」

Agent 帮你出了一版 settings、一个下拉菜单、一个确认弹窗。能点、能跳、能演示——但总差点意思：

1

按钮按下去没反馈，像点在平面海报上

2

弹层从屏幕正中「冒」出来，和触发按钮毫无关系

3

下拉用了ease-in，前半段发闷，后半段才冲出来

4

命令面板、快捷键也配华丽开场，用几次就觉得拖

产品同学拿去路演说「挺完整」。前端同学 review 时心里只有一句： 像 AI 写的 。

「问题往往不在会不会写动画，而在有没有一套可执行的手感标准。」


03

WHY

为什么 Agent 特别容易写出「AI 味」界面

会写代码 ≠ 知道手感

它知道 transition、scale、keyframes，却经常选错配方：进场该用 ease-out 却写成 ease-in；从 scale(0) 长出来；给一天上百次的操作也加动画，让高频路径变钝。

小细节会复利

单独看每一处都不算 bug。叠在一起，就是你说不清、但用户一秒能感到的廉价感。Emil 的判断很直白： Agents don't have great taste 。Skill 不是取代设计师，而是把领域经验放大到每一次生成和审查里。

原型和前端，其实是同一刀

原型阶段若定错运动语言，后面要么照搬烂动效，要么推倒重做。所以这套 skill 不只适合写 CSS 的人 ——做高保真原型、用 Agent 出可交互稿的同学，同样用得上。


04

WHAT

它是什么，又不是什么

项 说明
是什么 给 coding agent 用的 Design Engineering Skills，约束 UI / 动效决策
谁做的 Emil Kowalski（Sonner、Vaul；背景含 Vercel、Linear）
不是什么 不是 Figma 插件，不是组件库，不会一键「美化全站」

它提供三件事： 规则 、 审查 、 工作流 （先找机会 / 再审计 / 再执行）。

社区常把它和 Impeccable、Taste 并列：别人管版式与「去模板感」，Emil 这条线更擅长 motion 与克制。

兼容 Claude Code、Cursor、Codex 等常见 Agent 环境（以 Skills CLI 当前支持为准）。

06

WORKFLOW

两条可直接照抄的工作流

路径 A：产品 / 原型

目标不是「动效最多」，而是 演示时顺、日常用时不烦 。

STEP 01 先把结构和状态做对

先别急着加动画。

STEP 02 find-animation-opportunities

强制输出「建议 + 拒绝项」。

STEP 03 只采纳 3～5 个高杠杆动效

用 emil-design-eng 落地具体数值，演示前 review-animations 过一遍。

可复制 Prompt

. . . prompt

这是设置页，用户每天会进出几十次。

请用 find-animation-opportunities 的标准，列出真正值得加动效的点；

并明确写出你拒绝了哪些候选、为什么拒绝。

最多给 5 条建议，按杠杆排序。

路径 B：前端

1

新页面刚生成：先 shield，再动手

2

已有动效很乱：improve-animations 出 plan，再按 plan 改

3

PR 前：review-animations，要 Before / After / Why 表

自查清单（30 秒版）

☐ 有没有 transition: all

☐ 有没有从 scale(0) 进场

☐ UI 进场是否误用了 ease-in

☐ popover 是否从 trigger 长出

☐ 键盘 / 超高频操作是否还带着动画

☐ UI 动效是否普遍超过 300ms

☐ hover 是否考虑了触控误触发

☐ 是否处理了 prefers-reduced-motion

07

RULES

只记三条，也能立刻少踩坑

即使今天不装 skill，记住这三条，已经能挡住大半「AI 默认配方」。

1. 频率决定要不要动

出现频率 策略
100+ 次/天 不要动画
一天几十次 极短、极轻，或干脆去掉
偶尔（Modal / Drawer / Toast） 标准动效
很少 / 首次 才有资格谈一点 delight

2. 进场用 ease-out，别用 ease-in

用户盯的是「点下去之后有没有立刻动」。同样是 200ms，ease-in 会感觉更钝——因为慢在开头。

. . . css

--ease-out: cubic-bezier(0.23, 1, 0.32, 1);

3. 不要从虚无出现；popover 从按钮长出来

. . . css

/* 差 */ transform: scale(0);

/* 好 */ transform: scale(0.95); opacity: 0;

Before / After 速查

Before After Why
transition: all 只动画 transform 等 避免误伤与掉帧
scale(0) scale(0.95)+opacity 不从虚无出现
ease-in 下拉 ease-out / 强曲线 响应感在前半段
无 :active scale(0.97) 按下要有反馈
命令面板有动画 删掉动画 超高频 = 延迟

08

LIMITS

边界：别把它神化

1

装了不会自动变好看——要在对的时机调用：找机会、审查、审计。

2

动效只是「AI 味」的一部分；版式与文案仍可能很模板。

3

公开 skill 已够大多数原型与业务前端开工；课程版覆盖更广。

4

克制比花活重要——若扫完告诉你「几乎不该加动画」，那是好结果。

EPILOGUE

结语

好界面很少靠「多一个炫技动画」取胜。更多时候，是无数用户说不清的细节，在同一套标准下站在了一起。

Agent 已经很会交付「能用的界面」。差的那一层，往往是： 该不该动、怎么动、什么绝不动 。

你不需要先成为动效专家。你可以先给 Agent 一套更好的品味约束——然后在每一次原型和每一次 PR 里，复利下去。
